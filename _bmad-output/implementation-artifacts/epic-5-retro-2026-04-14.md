# Epic 5 Retrospective

## 1. Epic Review

### What Worked

- Epic 5 kept the right sequencing: persist run context first, execute against stored inputs second, then add result review and comparison.
- Reusing strategy configuration versioning and shared rule-evaluation logic avoided duplicating business semantics between screening and backtesting.
- The backtests area now behaves like a full workflow instead of a one-shot action: launch, explicit running state, execution, persisted summary, and cross-run review all exist.

### What Was Hard

- It was easy to overreach into analytics. The story boundaries needed discipline so the implementation stayed focused on reproducible run records and comparable summaries rather than premature performance metrics.
- Reproducibility semantics needed explicit representation. A checksum and persisted summary were necessary to make “same inputs, same result” concrete instead of implied.
- The backtests page accumulated responsibilities quickly once it had to support launch, execute, latest-run context, and multi-run review.

### Lessons Learned

- If reproducibility is a core promise, encode it in persisted artifacts early. Checksums and stable summary fields made that promise inspectable.
- Shared business logic should be extracted as soon as two workflows depend on the same conditions. Screening/backtesting alignment became much safer once condition evaluation was centralized.
- Review features move faster when run context is already durable and queryable; the later story mostly became composition work rather than schema redesign.

### Technical Debt / Follow-Up

- The `/backtests` page now spans launch, execute, status, review, and comparison concerns and will likely want decomposition if analytics expand.
- Backtest outputs are intentionally summary-level today; later stories may justify richer persisted result breakdowns if comparison needs deepen.
- There is still no standalone test coverage for frontend trust-state rendering in backtests, only lint/build validation.

## 2. Next Epic Preparation

### Ready Signals for Epic 6

- All major research workflows now exist: health, screening, detail review, watchlist, and backtests.
- The codebase now has enough cross-workflow state that trust, accessibility, and error semantics can be hardened consistently rather than speculatively.
- Existing data-health signals are already available and can be threaded into more workflow surfaces.

### Risks to Watch

- Trust messaging can easily drift if each route invents its own stale/partial/error wording.
- Accessibility improvements may expose UI components that currently work functionally but do not communicate state clearly enough for keyboard-only or non-color-dependent use.
- Hardening work can sprawl if it becomes a grab bag of unrelated polish instead of focusing on explicit acceptance criteria.

### Action Items

- Centralize workflow-level trust-state presentation where possible.
- Audit form and action surfaces for keyboard reachability and visible focus behavior before adding more features.
- Keep “error vs invalid input vs stale data vs partial data” distinctions explicit across all major workflows.
