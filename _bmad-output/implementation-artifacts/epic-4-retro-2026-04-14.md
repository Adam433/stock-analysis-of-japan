# Epic 4 Retrospective

## 1. Epic Review

### What Worked

- Epic 4 stayed incremental without losing workflow continuity. Add/remove came first, then research context persistence, then the dedicated review surface.
- The watchlist became a real domain instead of UI-local state. Entries now have stable persistence, canonical instrument linkage, and context fields that can survive across sessions.
- Reusing one watchlist control across the result list, stock detail, and watchlist view reduced drift and kept behavior consistent.

### What Was Hard

- The line between Stories 4.2 and 4.3 was easy to blur. Once note and observation-reason editing existed inline, it was tempting to over-build the review page before the dedicated story.
- Watchlist state propagation needed care. The result list, stock detail page, and watchlist page all wanted to reflect add/remove updates without diverging.
- Even a small research notebook workflow quickly accumulates UX state: add/remove, edit visibility, prefill, saved timestamps, and error handling all needed to stay legible.

### Lessons Learned

- Lightweight persistence features still benefit from explicit domain boundaries. Treating watchlists as a first-class backend domain made later context and review work straightforward.
- Shared UI actions are worth consolidating early when the same workflow appears in multiple surfaces.
- Added-date semantics should be defined when the field is introduced, not retrofitted later. Preserving it as a stable business field avoided accidental drift.

### Technical Debt / Follow-Up

- The shared watchlist control now owns a fair amount of state and may want decomposition if richer validation or bulk workflows are added later.
- There is still no optimistic cross-page cache for watchlist state, so each route owns its own fetch/update lifecycle.
- Backlinks from watchlist entries to originating screen or chart context are still shallow and could be expanded in later refinement.

## 2. Next Epic Preparation

### Ready Signals for Epic 5

- Strategy configurations are already versioned and persisted, so backtest runs can inherit exact parameter-set linkage.
- Market data, derived facts, screen runs, and stock-detail explainability are already aligned to stored inputs, which is the right foundation for reproducible backtests.
- The application shell now supports multi-workflow navigation, making it easier to add a separate backtests area without inventing a new app structure.

### Risks to Watch

- Epic 5 must not treat backtests as transient computations. Run records, date ranges, and parameter linkage need to be first-class from the start.
- It will be easy to accidentally loosen reproducibility by mixing “latest state” reads with persisted run context.
- Backtest launch UX needs explicit progress/status semantics, otherwise long-running work will feel ambiguous.

### Action Items

- Persist backtest runs before implementing result calculation so status and context are visible immediately.
- Reuse the existing strategy configuration versioning directly rather than inventing a separate backtest parameter snapshot shape.
- Keep result-review surfaces tied to persisted backtest run identifiers from the first story onward.
