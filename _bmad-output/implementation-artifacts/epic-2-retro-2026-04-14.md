# Epic 2 Retrospective

## 1. Epic Review

### What Worked

- Epic 2 kept a clean sequence: parameter configuration, derived-fact materialization, screen execution, then result-list presentation. Each story built on concrete persistence from the previous one.
- The project now has a real screening spine instead of placeholders. Parameters, derived facts, screen runs, and result lists are all persisted and queryable.
- Backend-first implementation paid off. By stabilizing storage and APIs before deep UI work, later stories could reuse existing behavior instead of replacing it.

### What Was Hard

- Semantics mattered as much as implementation. RPS, 52-week-high proximity, qualified-result traceability, and “latest run” behavior all needed explicit definitions before coding.
- The deeper the workflow became, the more easy it was for detail surfaces to drift from originating runs. That forced extra care around preserving run-linked facts instead of re-deriving them loosely.
- Frontend workflow complexity increased quickly once `/screen` had to handle configuration, execution, loading, empty states, and result summaries in one place.

### Lessons Learned

- When a workflow becomes stateful across stories, persist the intermediate artifacts early. Epic 2 worked because parameter sets, derived facts, and screen runs were all made first-class records.
- Route design needs to anticipate future consumers. Adding “latest run” retrieval before stock-detail work reduced friction for both UI and API integration.
- Test data should be shaped to prove the business rule, not just exercise the code path. Epic 2 surfaced several cases where naive monotonic price fixtures hid meaningful edge conditions.

### Technical Debt / Follow-Up

- The `/screen` page now owns multiple concerns and will likely need decomposition when stock-detail navigation and richer state handling arrive.
- Screening APIs are still thin and custom-shaped. Future result-list and stock-detail growth may justify explicit schema modules rather than inline dict payloads.
- There is still no frontend route for individual stock detail, only the backend payload service for it.

## 2. Next Epic Preparation

### Ready Signals for Epic 3

- Stock detail can now be anchored to persisted screen runs instead of ad hoc current-state calculations.
- Derived RPS and 52-week-high facts are already available in storage and can be reused directly for chart-adjacent explainability.
- The result list now exposes the exact identifiers and run context Epic 3 needs for drill-down.

### Risks to Watch

- Epic 3 must not let chart-ready payloads diverge from the stored result facts that qualified the stock.
- Once chart UI work starts, it will be tempting to compute convenience values client-side. That would weaken the consistency Epic 2 established.
- Payload size and response structure will start to matter more as candlestick series and RPS panels are added.

### Action Items

- Keep stock-detail responses explicitly tied to `screen_run_id` whenever the user is drilling down from a result list.
- Preserve backend authority for rule breakdown fields even if the frontend later adds chart transformations.
- Consider introducing dedicated response-schema modules once Epic 3 adds more complex detail payloads.
