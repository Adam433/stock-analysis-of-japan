# Epic 1 Retrospective

## 1. Epic Review

### What Worked

- The repo foundation stayed disciplined: new work was kept inside `apps/web` and `apps/api` instead of drifting back into legacy prototype paths.
- The team established a reliable trust backbone early: migrations, ingestion normalization, and explicit health visibility now exist before screening logic starts.
- Review loops caught real semantic problems rather than cosmetic ones, especially around idempotency, data-health truthfulness, and UI state meaning.

### What Was Hard

- Several stories looked “done” at implementation time but still had important correctness gaps that only appeared under review or richer test cases.
- Operational status semantics were easy to oversimplify. The difference between “last run succeeded” and “current dataset is trustworthy” required an extra correction pass.
- Frontend and backend integration now matters more: once the web shell started calling live API routes, environment and connectivity behavior became part of feature correctness.

### Lessons Learned

- For stateful backend work, treat “single happy-path test passed” as insufficient. Add tests for repeated runs, partial history, and mixed-state persistence before calling a story complete.
- When exposing trust signals, derive summary states from authoritative stored facts first, and use last-run metadata as supporting context, not the sole truth source.
- Story artifacts should be updated at the same time as code completion. Letting implementation files and sprint status drift creates avoidable ambiguity during handoff.

### Technical Debt / Follow-Up

- The current web app still relies on direct environment-based API URLs. A cleaner cross-app runtime configuration strategy would reduce local setup fragility.
- Backend API coverage is still service-heavy rather than endpoint-heavy. Future stories should add route-level tests once more HTTP workflows exist.
- Screening-related domains are only starting now; the repo needs consistent conventions for domain models, route naming, and run persistence before Epic 2 expands.

## 2. Next Epic Preparation

### Ready Signals for Epic 2

- Market data and freshness visibility are in place, so later screen results can inherit a trustworthy dataset baseline.
- FastAPI routing, SQLite migrations, and Next.js integration are established and verified, reducing startup risk for screen configuration workflows.
- The review process is now calibrated toward behavioral correctness, which is exactly what Epic 2 needs for parameter persistence and explainable runs.

### Risks to Watch

- Strategy configuration must avoid becoming a UI-only state; later screen and backtest runs need a persisted, versioned parameter source of truth.
- Epic 2 introduces tighter coupling across web forms, API validation, persistence, and future screening runs. If naming drifts now, downstream stories will pay for it.
- Validation semantics need to be explicit at the boundary. Ambiguous threshold meanings will create confusion in both result logic and chart explanations later.

### Action Items

- Keep strategy parameters versioned rather than mutable-in-place when that improves future run traceability.
- Add boundary tests whenever a new story introduces persisted user-controlled inputs.
- Preserve the habit of code review before story closeout; Epic 1 showed it is finding real issues, not process overhead.
